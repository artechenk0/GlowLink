# Specification-driven development (SDD)

SDD помогает согласовать ожидаемое поведение до реализации и сохранить доказательства того, что
оно проверено. Для каждой существенной задачи ведите отдельную папку
`docs/specs/<slug>/` на основе [шаблона](specs/_template/README.md).

Используйте SDD для изменения пользовательского поведения, CLI, GUI, протокола, совместимости,
архитектурных границ или поддерживаемого устройства. Простые исправления текста и механические
изменения без влияния на поведение не требуют отдельной спецификации.

## Жизненный цикл

| Стадия | Что происходит | Условие перехода |
| --- | --- | --- |
| `business-draft` | Описаны проблема, пользовательская ценность, границы и критерии успеха. | Пользователь явно одобрил бизнес-часть. |
| `technical-draft` | Добавлены технический подход, небольшие задачи и способ проверки каждой. | Пользователь явно одобрил техническую часть. |
| `ready-to-apply` | Оба согласования зафиксированы во front matter. | Можно начинать реализацию. |
| `applied` | Выполнены задачи, а результаты запланированных проверок записаны в спецификацию. | Реализация передана на независимую проверку. |
| `verified` | Критерии успеха сопоставлены с доказательствами, а документация синхронизирована. | Работа завершена. |

Записывайте стадию и согласования во front matter файла `README.md`. После `applied` не
расширяйте объём существующей спецификации: для нового объёма создайте новую запись и
согласуйте её заново.

## Структура спецификации

| Файл | Содержимое |
| --- | --- |
| `README.md` | Название, stage, approvals, краткий статус и ссылки на части спецификации. |
| `story.md` | Бизнес-цель, user story, границы и критерии успеха. |
| `technical.md` | Технический подход, затронутые границы и стратегия проверки. |
| `tasks.md` | Задачи, журнал реализации, результаты проверки и синхронизированная документация. |

## Команды

- `$sdd-propose <идея или путь к папке спеки>` создаёт business draft и после согласований развивает его до
  `ready-to-apply`.
- `$sdd-apply <путь к папке спеки>` выполняет только технически одобренную спецификацию, отмечает
  задачи и записывает выполненные команды. Результат этой команды — `applied`, не `verified`.
- `$sdd-verify <путь к папке спеки>` сопоставляет результат с критериями, проверяет документацию и
  переводит запись в `verified` только при наличии требуемых доказательств.

## Доказательства и документация

Для каждой задачи укажите автоматический тест, команду проверки или ручной шаг. Для GUI приложите
или запросите скриншот. Для BLE отдельно фиксируйте ручной прогон устройства в
`docs/hardware-tests/`; фейковые тесты не заменяют его. Не называйте hardware-тест выполненным,
пока в спецификации нет результата прогона.

При проверке обновляйте только относящиеся к изменению документы: README для UX или CLI,
`docs/product-scope.md` для границ продукта, protocol notes и матрицу совместимости для
подтверждённого протокола или устройства. Решение, изменяющее архитектурную границу,
совместимость или поддерживаемое поведение, фиксируйте отдельным [ADR](decisions/README.md).

Полный учебный пример находится в
[example-device-status](specs/example-device-status/README.md). Он показывает формат `verified`,
но не является историческим отчётом и не подтверждает hardware-тест.
